# Maintaining This Plugin

Guidance for editing the plugin itself. Nothing in this file is loaded at runtime; do not reference it from SKILL.md.

- Layout: the plugin root holds `.claude-plugin/plugin.json` and `hooks/`; the skill lives in `skills/implementation-journal/` with its `references/`, `scripts/` and `agents/`. The repo root's `.claude-plugin/marketplace.json` lists the plugin. Marketplace installs are copied to a cache, so everything the plugin uses must stay inside this folder; `../` paths do not load. For Codex, copy `skills/implementation-journal/` on its own.
- The record is one file per task with three sections: For People, Decided, Next. It was a folder of four files (brief, log, handoff, restart note) until 2026-11-14. Two trials that day decided the change. On a small made-up project, fresh sessions without any record recovered everything the code and git could show and lost exactly the two decisions written nowhere else; a 160-word single file did as well as the 490-word folder. On a hard real task (pydantic-ai #12556), continuing from a 381-word single file gave the same test results as continuing from the 1,960-word folder, at lower cost, and both took about half the time of continuing with no record. So the record holds only what code and git cannot show, plus the lines for people. Before adding a section or a second file, run the same kind of trial: the same task continued with and without the addition.
- When changing SKILL.md or the reference, validate with fresh sessions if the environment supports them. Give each one a realistic task and the skill, not your expected answer.
- Each rule lives in exactly one place: when to write and what belongs in SKILL.md; the format and the meaning of each line in `references/task-file.md`. Before adding text, search the other file for a restatement of the same rule and consolidate instead of duplicating.
- Several sessions may work in one repo at once. Nothing the skill writes may be a single repo-wide file that each session rewrites: that is why there is no index and no shared restart file. `hooks/session_start.py` derives the list of open tasks by scanning the records. Keep it that way when adding features.
- Older projects keep the folder form. The skill tells sessions to leave those folders alone and keep writing in their `handoff.md`; `session_start.py`, the validator and `bearings.py` all still read them. The repo-level `docs/tasks/NEXT-SESSION.md` of the form before that is read only by the hook. Do not remove this reading while such projects exist.
- One section of a record is read by a program outside this plugin: `## For People`. `bearings/skills/bearings/scripts/bearings.py` (`read_handoff`, `load_tasks`) parses its heading and its keys (`Name`, `Now`, `Needs you`, `Next` for where the task stands; `Done`, `Try`, `Not yet`, `Added`, `Changed`, `Removed` for what its last finished step came to; or the Chinese ones) and the map page shows them to a person, the marks drawn on the parts list's flow diagrams (format `Part / Box: sentence`, parsed by `MARK_RE` and `place_marks`). It also reads the header's `status:` and `updated:`, and the file's git history for the task's story. `hooks/session_start.py` reads `Name` and `Now`. Change the heading, a key or the header in all of these or not at all.
- `skills/implementation-journal/agents/openai.yaml` is metadata for a non-Claude harness; Claude Code ignores it. Keep it only while the skill is used with that harness.
- `hooks/hooks.json` registers the two hook scripts through the plugin. `hooks/post-edit-validate.sh` finds the validator at `skills/implementation-journal/scripts/validate_journal.py` relative to the plugin root; keep that path and the `docs/tasks/` pattern in sync with SKILL.md. hooks/README.md keeps a manual settings.json snippet only for setups where the plugin is not loaded; never both, or every hook runs twice. Do not add a `paths:` frontmatter field to SKILL.md: it limits auto-loading to sessions that touch matching files, which would stop the skill triggering before a record exists.
- `scripts/validate_journal.py` mechanically mirrors rules that live in SKILL.md and `references/task-file.md` (the header, the three sections, the lines for people, the read budget, relative dates, template placeholders). When editing those rules, update the script's checks in the same change, and rerun it against one known-good and one deliberately broken record before shipping.
