# Maintaining This Plugin

Guidance for editing the plugin itself. Nothing in this file is loaded at runtime; do not reference it from SKILL.md.

- Layout: the plugin root holds `.claude-plugin/plugin.json` and `hooks/`; the skill lives in `skills/implementation-journal/` with its `references/`, `scripts/` and `agents/`. The repo root's `.claude-plugin/marketplace.json` lists the plugin. Marketplace installs are copied to a cache, so everything the plugin uses must stay inside this folder; `../` paths do not load. For Codex, copy `skills/implementation-journal/` on its own.
- The record is one file per task with three sections: For People, Decided, Next. It was a folder of four files (brief, log, handoff, restart note) until 2026-11-14. Two trials that day decided the change. On a small made-up project, fresh sessions without any record recovered everything the code and git could show and lost exactly the two decisions written nowhere else; a 160-word single file did as well as the 490-word folder. On a hard real task (pydantic-ai #12556), continuing from a 381-word single file gave the same test results as continuing from the 1,960-word folder, at lower cost, and both took about half the time of continuing with no record. So the record holds only what code and git cannot show, plus the lines for people. Before adding a section or a second file, run the same kind of trial: the same task continued with and without the addition.
- When changing SKILL.md or the reference, validate with fresh sessions if the environment supports them. Give each one a realistic task and the skill, not your expected answer.
- Answers to a plan (2026-11-24). A plan page such as html-plan's is where the user picks between options before building, and nothing carried those picks into a record: the page is not where the next session looks. Tried with fresh Sonnet sessions given a pasted plan response and told that part of the work was for later. With the description as it was, two of two sessions built the code and neither loaded this skill nor wrote a record; a sentence in the body cannot help a skill that is not loaded. After the description named this case ("pastes back their answers to a plan", "part of it is left for later"), six of six loaded it and wrote the decisions down. The finer rule, that an answer the user never opened is a guess and not a decision of theirs, is not reliable: it was ignored once, followed three times (two of those with an example that happened to match the test, so they prove little), and once applied to the wrong answer. It took quoting html-plan's own marker and giving an example line to get that far. Keep the example unrelated to whatever is used to test it.
- Each rule lives in exactly one place: when to write and what belongs in SKILL.md; the format and the meaning of each line in `references/task-file.md`. Before adding text, search the other file for a restatement of the same rule and consolidate instead of duplicating.
- Several sessions may work in one repo at once. Nothing the skill writes may be a single repo-wide file that each session rewrites: that is why there is no index and no shared restart file. `hooks/session_start.py` derives the list of open tasks by scanning the records. Keep it that way when adding features.
- A record says how things stood on the day it was written, and nothing closes a task its owner walked away from. Since 2026-11-24 `hooks/session_start.py` prints every record with the day it last changed and its age, and names instead of printing one that has not changed in over `STALE_DAYS` (30, the same as `RECENT_DAYS` in `bearings.py`, which drops such a task from the map; keep the two equal). What prompted it: a project whose every new session was handed a 62-day-old restart note saying a run was in progress and must not be restarted. The hook only reports the age; it does not close, edit or hide the record from a session that opens it. Checked by running the hook on real projects and on made-up records (committed long ago and freshly checked out, uncommitted, ignored by git, outside git); not tried with a fresh session.
- Which tasks are in progress is decided in two places that must agree: `open_tasks` in `hooks/session_start.py` and `tasks_shown` in `bearings.py`. Until 2026-11-24 the hook listed an older folder only when it had a `next-session.md`, so a task could stand on the map with two things waiting on the user and be missing from the list a new session was given. Both now go by: not Complete, and either lines for people or a change in the last 30 days (the hook also keeps a folder that has a `next-session.md`). Do not widen it to every folder not marked Complete: old projects have dozens that never were, some with no `status:` at all.
- Older projects keep the folder form. The skill tells sessions to leave those folders alone and keep writing in their `handoff.md`; `session_start.py`, the validator and `bearings.py` all still read them. The repo-level `docs/tasks/NEXT-SESSION.md` of the form before that is read only by the hook. Do not remove this reading while such projects exist.
- One section of a record is read by a program outside this plugin: `## For People`. `bearings/skills/bearings/scripts/bearings.py` (`read_handoff`, `load_tasks`) parses its heading and its keys (`Name`, `Now`, `Needs you`, `Next` for where the task stands; `Done`, `Try`, `Not yet`, `Added`, `Changed`, `Removed` for what its last finished step came to; or the Chinese ones) and the map page shows them to a person, the marks drawn on the parts list's flow diagrams (format `Part / Box: sentence`, parsed by `MARK_RE` and `place_marks`). It also reads the header's `status:` and `updated:`, and the file's git history for the task's story. `hooks/session_start.py` reads `Name` and `Now`. Change the heading, a key or the header in all of these or not at all.
- `skills/implementation-journal/agents/openai.yaml` is metadata for a non-Claude harness; Claude Code ignores it. Keep it only while the skill is used with that harness.
- `hooks/hooks.json` registers the three hook scripts through the plugin. Each `.sh` file is a few lines: it sources `hooks/python.sh` to find a Python 3 and runs the `.py` file of the same name, where the logic is. Keep it that way: paths, JSON and Windows are handled in Python, not in shell. `hooks/post_edit_validate.py` finds the validator at `skills/implementation-journal/scripts/validate_journal.py` relative to the plugin root; keep that path and its `TASKS` pattern in sync with SKILL.md. Nothing here has been run on Windows (see hooks/README.md). hooks/README.md keeps a manual settings.json snippet only for setups where the plugin is not loaded; never both, or every hook runs twice. Do not add a `paths:` frontmatter field to SKILL.md: it limits auto-loading to sessions that touch matching files, which would stop the skill triggering before a record exists.
- `scripts/validate_journal.py` mechanically mirrors rules that live in SKILL.md and `references/task-file.md` (the header, the three sections, the lines for people, the read budget, relative dates, template placeholders). The length is counted in words since 2026-11-24 (`count_words`, with two Chinese characters as one word, and a warning past `MAX_WORDS`): until then only lines were counted, and the one real one-file record had grown to about 1,000 words against an aim of 300 to 400 without a warning. 600 is a chosen number, half as much again as the aim; nobody has measured where a longer record starts to cost more than it gives. SKILL.md names what the script checks, so that a session knows the rest is its own to check; keep that sentence true. When editing those rules, update the script's checks in the same change, and rerun it against one known-good and one deliberately broken record before shipping.
- `scripts/decided.py` is how a decision in a finished record reaches a later session: given files, it prints the `Decided` lines of every record whose commits changed them. It was added on 2026-11-24 in place of an index, which stays ruled out (see the bullet on several sessions). It reads the same things `bearings.py` reads to place a task (`task_rooms`, `older_commits`): the hashes a record cites, and the commits that changed that record and no other task's. Keep the two in step, with one difference since 2026-11-24: `decided.py` follows a file to the name it has now (`follow`: the renames git reports in the commits after the record's work, applied oldest first, and only those made after that work, so a new file that reuses an old name is not mistaken for the old one), because a rule that stops coming up when its file moves is the failure this script exists to prevent. `bearings.py` does not follow renames: the map places past work by the paths it had. A file split in two, or moved and mostly rewritten in one commit, is not a rename to git and is not followed. It reads `## Decided`, and `## Key Decisions` / `## Closed Decisions` in an older `handoff.md`. `hooks/session_start.py` ends its output with one line naming this script whenever the repo has finished records, and prints that line alone when no task is open; the line gives the script's absolute path, worked out from the hook's own place in the plugin, so keep `hooks/` and `skills/implementation-journal/scripts/` where they are. Tried on 2026-11-24 with fresh sessions asked for a change that an earlier decision forbids; the README says what came of it.
- `hooks/decided_on_edit.py` (added 2026-11-24, after that trial showed a session without the reminder can miss a rule) gives the same lines without being asked: after a session's first edit to a file it imports `decided.py`, calls `look_up` and returns the records as PostToolUse `additionalContext` (plain stdout from a tool hook does not reach the model). It must never block, fail or undo an edit: it reports only, and any error ends it silently. So that a record is given once per session it keeps a note per session in the temporary folder; `session_start.py` empties that note after a compaction or `/clear` (`forget`) and marks a record it printed whole (`remember`). A subagent has its own note. Checked on made-up and real repositories, and once end to end: a fresh Sonnet session asked only to add a comment line quoted the hook's lines back. Not tried: whether a session that gets a rule this way, after its first edit, goes back and corrects that edit.
